# Пилот Black Arachne 0.7 в режиме наблюдения

## Область пилота

Начните с одного разрешённого тестового хоста Ubuntu 24.04 с systemd, OpenSSH и Python 3.12. Black Arachne собирает журнал, связывает события входа с активностью `sudo` и предлагает выводы оператору. По желанию можно наблюдать за целостностью отдельной папки. В штатной конфигурации обе роли работают локально. Программа читает телеметрию и записывает собственное состояние. Решения о действиях на хосте остаются у оператора.

Пилот начинается после того, как оператор подтвердил чтение журнала и наличие связанных сессий на своём хосте. На некоторых версиях OpenSSH запись об успешной аутентификации появляется прежде, чем Linux присвоит идентификатор. Для привязки подходят записи PAM об открытии сеанса или записи OpenSSH `Starting session` уровня `VERBOSE`. Если доступна только запись об аутентификации, уточните настройки журналирования OpenSSH в утверждённой конфигурации тестового хоста. Проверка GitHub Actions повторяет этот сценарий на одноразовой Ubuntu VM с двумя обычными SSH-подключениями. Она проверяет, что принятый запрос `sudo` относится только к нужному сеансу, что отказ записывается отдельно и что поздняя запись открывает на повторный разбор только связанный сеанс. Проверку можно запустить вручную во вкладке Actions в публичном репозитории.

## Проверки разработчика

Набор тестов можно запускать в рабочей Linux-среде и в изолированном Ubuntu-контейнере. Для приёмки установленной службы и нативных полей аудита используйте задание `pilot-native` в GitHub Actions. Оно запускается на стандартной временной Ubuntu VM. SSH-сервер для проверки слушает только loopback. Секреты проекта и рабочие журналы для этого задания не требуются.

## Установка на тестовый хост

Выполните команды из корня распакованной версии проекта. Они создают отдельный аккаунт службы и устанавливают файлы systemd. На хосте с существующей установкой сначала используйте его обычный порядок обновления и сохраните состояние базы.

```sh
getent passwd black-arachne >/dev/null || \
  sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin black-arachne

sudo install -d -m 0755 /opt/black-arachne
sudo cp -a arachne /opt/black-arachne/
sudo install -m 0644 deploy/black-arachne.service deploy/black-arachne.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start black-arachne.service
sudo systemctl enable --now black-arachne.timer
```

Служба автоматически создаёт базу `/var/lib/black-arachne/evidence.sqlite3` под своим именем. Таймер запускает следующий цикл через две минуты после завершения предыдущего. Для проверки используйте:

```sh
sudo journalctl -u black-arachne.service --since today
sudo -u black-arachne sh -c 'cd /opt/black-arachne && python3 -m arachne --db /var/lib/black-arachne/evidence.sqlite3 pilot-report'
```

Для локального просмотра из доверенной оболочки на хосте:

```sh
sudo -u black-arachne sh -c 'cd /opt/black-arachne && python3 -m arachne --db /var/lib/black-arachne/evidence.sqlite3 serve --operator'
```

Панель слушает адрес `http://127.0.0.1:8765/`. Режим оператора рассчитан на одного доверенного локального пользователя. В отчёт для обсуждения включайте агрегаты команды `pilot-report`. Храните журналы, базу, подтверждения и ключи по правилам выбранного хоста.

## Приёмка первого хоста

1. Выполните две штатные SSH-сессии с одного тестового аккаунта. В одной выполните разрешённую безвредную команду через `sudo`. Проверьте, что система связала активность с правильным сеансом.
2. Проверьте `journal.bound_observations` и свежую запись о сборе в `operations.collector`. Поле `operations.collector.coverage` показывает размер последней выборки, сколько записей нормализовано и в скольких отсутствовал путь к исполняемому файлу. `journal.sudo_denials_unverified` учитывает наблюдения о возможном отказе отдельно от подтверждённых отказов. Входы, у которых Linux не выдал идентификатор аудита, имеют статус «непривязанный» и видны оператору отдельно.
3. Для немедленной проверки можно выбрать вход командой `anchors` и выполнить `investigate HOST ANCHOR_ID --offline`. Штатный цикл создаёт досье после окна наблюдения в 15 минут.
4. Если пилот включает целостность файлов, создайте исходный снимок тестовой папки. Измените контрольный файл и убедитесь, что появился один результат с ожидаемыми хэшами и правами.
5. Подтвердите несколько исходов в панели и проверьте, что счётчик `cases.decisions_confirmed` растёт. Если в окно дела позже приходит прямая запись того же сеанса или независимое подтверждение, служба создаёт новую версию досье. Оцените новый снимок отдельно.

## Как оценивать пользу Red

В `pilot-report` каждая строка результатов сравнивается с решением оператора по последней версии дела. Обычная проверка и Red получают по одному дополнительному чтению. Детерминированный ориентир читает три. Смотрите на ложные и пропущенные эскалации, а также на пары, где помог только один из двух одношаговых вариантов. Счётчики прогнозов показывают, как часто Red делает прогноз и как часто совпадает с Blue. До оценки отдельно запишите желаемые пороги для ложных тревог, времени работы оператора и числа проверенных дел.

Встроенные сценарии подходят для воспроизводимости сборки. Для оценки качества на ваших данных используйте выводы вашего оператора или отдельный закрытый набор. Утилита `evaluate FILE --offline` сравнивает три решения и ориентир на таком наборе.

## Остановка

Остановите таймер и службу, если наблюдение нужно приостановить. База хранится отдельно и остаётся доступной для последующего разбора.

```sh
sudo systemctl disable --now black-arachne.timer
sudo systemctl stop black-arachne.service
```

### Файловые сигналы Linux Audit

Импортируйте доверенный сырой экспорт Linux Audit одной загрузки. Настройку правил аудита выполняет оператор Ubuntu на своей пилотной машине. Для начального прогона используйте два одновременных SSH-сеанса одного пользователя и отдельную тестовую папку. Снимите журнал OpenSSH с нативными метаданными, зарегистрируйте тестовый файл-приманку и подготовьте JSON-карту абсолютных путей к ID зарегистрированных приманок. Идентификаторы машины и загрузки должны относиться к тому же экспорту.

```sh
python3 -m arachne --db linux.sqlite3 dead-souls import-audit audit.raw \
  --key sensor.key.json --machine-id MACHINE_ID --boot-id BOOT_ID \
  --watch-key arachne_pilot --decoys decoys.json --burst-threshold 25
```

Импорт связывает `SYSCALL` и `PATH` по идентификатору Linux Audit, учитывает успешные `open`/`openat` на x86-64 и `openat` на aarch64. Для команд, которые открывают файл с правом записи, отчёт показывает число разных путей на PID, сеанс и календарную минуту. Право записи не доказывает изменение содержимого или вредоносность. Сравнивайте сигнал с журналом согласованных работ и штатным резервным копированием. Отсутствующий или неоднозначный сеанс оставляет событие приманки без привязки. Сборщик сообщает о потерях отдельными подписанными записями о пробелах. Импорт не восстанавливает записи, которых нет в экспорте, и не охватывает `openat2`, операции через уже открытые дескрипторы и события за пределами правил. Не смешивайте выгрузки нескольких загрузок в одном пакете.

### Обратимый карантин

Создайте закрытый каталог с правами `0700` на той же файловой системе. Укажите хэш, который оператор сверил, и причину решения.

```sh
python3 -m arachne quarantine isolate /path/to/sample \
  --vault /path/to/vault --sha256 APPROVED_SHA256 --reason 'Номер дела и причина' --execute
python3 -m arachne quarantine restore RECEIPT_ID --vault /path/to/vault --execute
```

Перемещение сохраняет исходный inode и права. Квитанция содержит исходный путь, хэш, время и причину. Восстановление проверяет файл, исходный каталог и наличие другого файла на месте назначения. Карантин рассчитан на обычные файлы в каталогах, контролируемых оператором. Уже открытые дескрипторы сохраняют доступ, поэтому для активного процесса требуется отдельное решение оператора.

### Сравнение роя и одиночной проверки

При равном бюджете одного дополнительного чтения на пару запустите `compare-signals` на раздельных выборках. В поставляемой лабораторной выборке восемь отложенных пар: одиночная проверка различила пять, вариант со сменой ролей — четыре и в одной паре перепутал решения. Это результат для выбора источника улик. Для оценки на реальных данных нужна отдельная закрытая выборка с подтверждёнными исходами.
