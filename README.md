# Black Arachne

Black Arachne 0.7 — защитное расследование Linux-инцидентов в режиме наблюдения. Он импортирует метаданные OpenSSH и sudo из Linux journal, собирает досье по входу SSH, фиксирует прогноз Red и сравнивает три варианта решения. Интерфейс показывает прогноз, решение каждого варианта, хронологию улик и изменения отслеживаемых файлов.

## Быстрый запуск

Нужен Python 3.12. Сторонних пакетов и ключа API для обычного запуска не требуется.

```sh
python3 -m arachne --db trial.sqlite3 trial --offline
python3 -m arachne --db trial.sqlite3 serve
```

Для развёртывания на тестовом Ubuntu-хосте и критериев оценки используйте [руководство пилота](docs/pilot.md).

Откройте [локальную панель](http://127.0.0.1:8765). Начните с `repeated-failures-and-account-confirmation`: прогноз Red направляет Blue к сведениям об учётной записи, и Blue оставляет дело на ручной проверке. Затем откройте `identity-dispute-with-declaration`: варианты с одной проверкой упускают эскалацию, а отдельная политика фиксирует независимое возражение. Панель показывает ожидаемое решение и выделяет несовпадения. Команда `demo` сохраняет пять примеров прежнего механизма для сравнения с 0.2.

Пакет можно установить из уже собранного wheel в отдельное окружение одновременно с демонстрацией:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install --no-index --no-deps ./black_arachne-0.7.0-py3-none-any.whl
.venv/bin/black-arachne --db trial.sqlite3 trial --offline
.venv/bin/black-arachne --db trial.sqlite3 serve
```

## Данные реального Linux-хоста

Оператор запускает команды из каталога проекта. Используйте учётную запись с разрешённым чтением соответствующих записей journal. Для удалённого тестового Linux-хоста можно сохранить такой же экспорт и передать его локальной команде `import-journal`. Для реальных событий заведите отдельное хранилище.

```sh
set -o pipefail
journalctl --since '30 minutes ago' --no-pager -o json \
  SYSLOG_IDENTIFIER=sshd SYSLOG_IDENTIFIER=sshd-session SYSLOG_IDENTIFIER=sudo |
  python3 -m arachne --db linux.sqlite3 import-journal --native

python3 -m arachne --db linux.sqlite3 anchors
python3 -m arachne --db linux.sqlite3 investigate HOST ANCHOR_ID
python3 -m arachne --db linux.sqlite3 serve
```

Импорт сохраняет хост, время UTC, тип, идентификатор события, имя пользователя и источник. Полное сообщение journal, аргументы команд и IP из него отбрасываются. Повторный импорт тех же строк не создаёт дубликатов. При конфликте идентификатора импорт откатывается целиком. Расследование охватывает от 10 минут до входа до 15 минут после него. События связываются с одним сеансом по идентификаторам машины, загрузки и сеанса аудита Linux. Соседние события, у которых нет такой связи, видны в досье отдельно и не влияют на вывод о данном сеансе. Вход без доступного идентификатора может остаться на ручной проверке.

Операторы могут загрузить контекст через `import-events FILE.jsonl`. Каждая строка — JSON-объект с полями `id`, `timestamp`, `host`, `kind`, `actor` и `source`. Поля `machine_id` и `session_key` добавляются при нормализации журнала, если соответствующие метаданные доступны. Для журнала изменений предусмотрены `deployment`, `change_verified` и `change_disputed`. Для учётных записей — `identity_verified` и `identity_disputed`. Автоматический сбор локального журнала проверяет системное поле `_EXE` по известным путям OpenSSH и sudo. Ручной импорт из файла предназначен для экспорта из известной оператору среды.

### Подтверждение независимых сведений

Изменения и сведения об учётной записи влияют на решение после проверки HMAC и привязки к конкретному ID входа. Обычный импорт оставляет такую запись в хронологии со статусом «Подтверждение не прошло проверку источника». Для локальной проверки можно провести весь цикл:

```sh
python3 -m arachne create-verifier /safe/path/change.key.json --id lab-change --source change-management --host HOST
python3 -m arachne sign-verifications confirmations.jsonl --key /safe/path/change.key.json --anchor ANCHOR_ID > signed.jsonl
python3 -m arachne --db linux.sqlite3 import-verifications signed.jsonl --key /safe/path/change.key.json
python3 -m arachne --db linux.sqlite3 triage --offline
```

Ключ разрешает подтверждения одного источника и хоста. Отдельные записи должны иметь собственные идентификаторы событий и время в окне соответствующего входа. Поле `source` для таких записей принимает `change-management` или `identity-management`. Импорт проверяет HMAC, хост, учётную запись, временное окно и ID входа. При поступлении нового подтверждения автоматический разбор создаёт новое досье, сохраняя старое. Для HMAC обе стороны имеют доступ к одному секрету. Рабочий ключ хранится за пределами репозитория, с доступом только у аккаунта оператора и доверенного источника.

## Как устроено расследование

В локальном режиме Red, Blue и обычный рецензент работают в трёх дочерних процессах. Координатор обменивается с ними сообщениями через стандартный ввод и вывод. У каждого процесса свой набор операций и представление данных. Досье показывает последовательность обмена. При сбое процесса автоматический разбор сохраняет задание для повтора и продолжает обработку других входов.

- **Blue** видит доступную историю событий, формулирует две конкурирующие гипотезы и заранее фиксирует ожидаемые результаты проверок.
- **Red** видит только сводку и проверенные исторические решения по похожим случаям. Он делает прогноз исходного решения Blue и предлагает одну из трёх проверок: журнал изменений, сведения об учётной записи или последовательность событий.
- **Независимый рецензент** получает те же данные и выбирает одну проверку. Координатор фиксирует прогнозы до открытия дополнительных сведений. В обоих вариантах одна проверка и одинаковые правила пересмотра решения. Если выбрана одна и та же проверка, координатор использует один результат.
- **Итоговая защитная политика** применяет известные независимые признаки риска отдельно от сравнения. Досье содержит исходные сведения, ход проверки, решение каждого варианта и итоговую рекомендацию.
- **Панель** слушает loopback и показывает результаты в режиме чтения. Поддерживаемая среда запуска — один локальный оператор. Для сетевого развёртывания понадобятся аутентификация, авторизация и отдельное инженерное ревью.

### Red и Blue с моделью

Задайте `OPENAI_API_KEY` через окружение и добавьте `--model gpt-5.4-mini` после `trial`, `evaluate` или после аргументов `investigate`. Red и независимый рецензент получают одинаковую сводку без идентификаторов. Blue получает типы событий, относительное время и локальные псевдонимы улик. Ответы проверяются по схеме. Контекст, который модель видит, зависит от роли, а раскрытие дополнительных сведений и итоговая политика выполняются локально.

Краткие термины, ограничения и сценарии проверки описаны в [спецификации прототипа](docs/prototype.md).

## Проверка

```sh
python3 -m unittest discover -s tests -v
```

Лабораторная выборка мала, заранее известна и служит проверкой сборки. Для оценки вклада Red нужны закрытые семейства эпизодов и сравнение с обычной дополнительной проверкой при одинаковом бюджете. Режим запуска исследовательский: программа формирует защитные рекомендации. Любые операции на хостах остаются за оператором.

## Регулярный сбор и разбор

Команда `cycle` сохраняет курсор локального журнала при успешном импорте и разбирает готовые SSH-входы. Разбор начинается после полного 15-минутного окна наблюдений. Расследование повторяется после поступления нового аутентифицированного подтверждения. Ручное расследование также позволяет повторно оценить эпизод. Та же команда проверяет настроенные наблюдения за файлами. Ошибка чтения журнала отображается отдельно, поэтому проверка папок и разбор уже собранных событий могут продолжаться.

```sh
python3 -m arachne --db linux.sqlite3 cycle
python3 -m arachne --db linux.sqlite3 serve
```

В `deploy/` лежат шаблоны службы и таймера systemd для тестового хоста. Они предполагают Python 3.12 по указанному в unit-файле пути, каталог кода `/opt/black-arachne`, отдельного системного пользователя и явно выданное право читать требуемый журнал. Планировщик запускается каждые две минуты после завершения предыдущего цикла. Для просмотра служебной базы нужен тот же локальный пользователь или отдельно разрешённый доступ. SQLite обслуживает один локальный экземпляр. Следите за доступным диском и архивируйте данные по принятой политике хранения.

Опция `--offline` принудительно выбирает локальный режим. Режим с внешними моделями для обеих ролей включается опцией `--model` у `cycle`, `triage`, `investigate`, `trial` и `evaluate`. Поставляемая служба запускает цикл с опцией `--offline`. Внешняя модель доступна в отдельно запущенном процессе с явным `--model` и настроенным `OPENAI_API_KEY`. Red формирует прогноз до ответа Blue. Независимый рецензент получает тот же каталог проверок. Координатор применяет общий механизм пересмотра к результату каждой проверки. Локальная политика отдельно требует подтверждения заявленного изменения для закрытия и сохраняет наблюдаемые признаки повышенного риска. При ошибке вызова модели команда сообщает о сбое. Уже записанные события и курсор сохраняются, следующий запуск может повторить разбор.

## Локальный режим оператора

Панель может подтверждать итог реального расследования. Для этого запустите её командой `python3 -m arachne --db linux.sqlite3 serve --operator`. По умолчанию панель доступна только для чтения. В режиме оператора запись разрешена с того же локального адреса и защищена случайным токеном сеанса. Режим предназначен для одного доверенного оператора за локальным компьютером.

`python3 -m arachne --db linux.sqlite3 status` показывает успешную проверку журнала, количество расследований и число событий, исключённых из авторазбора. Если окно содержит больше 1000 событий, этот эпизод отмечается отдельно, а остальные продолжают обрабатываться.

Каждое новое подтверждённое решение добавляется в журнал с контрольной суммой и ссылкой на предыдущее. Команда `python3 -m arachne --db linux.sqlite3 verify-audit` сравнивает цепочку с хранимыми решениями и возвращает код 2 при расхождении. Решения, перенесённые из версий до 0.4, учитываются отдельно. Контроль обнаруживает частичную порчу данных внутри базы. Для доказательства целостности при полном доступе к базе отдельно сохраняйте контрольную сумму, которую выводит команда.

## Память и закрытая оценка

Оператор может сохранить сверенный исход реального расследования:

```sh
python3 -m arachne --db linux.sqlite3 confirm-outcome RUN_ID review --note 'Сверено с заявкой на изменение'
```

Следующее расследование может использовать до пяти разных подтверждённых эпизодов того же хоста и профиля. Локальный Red строит распределение решений Blue по наблюдавшимся результатам. Он прогнозирует решение при достаточной истории и большинстве за один исход. Эффективность проверок оценивается отдельно по подтверждённым решениям оператора. Локальный Blue уточняет ожидаемый результат проверки по подтверждённым исходам. Выбор защитной проверки и ожидания Blue меняются после как минимум трёх согласующихся прецедентов. В режиме внешнего API в запрос добавляются только структурированные итоги расследований. Текст заметки и идентификаторы хоста, пользователя и события остаются локально.

Для сравнения на закрытом наборе используйте `python3 -m arachne evaluate DATASET.jsonl`. Каждая строка содержит `id`, `family`, `expected`, `anchor_id` и массив `events` в формате импорта. Итог содержит точность вариантов, пропущенные и ложные эскалации, результат по семействам и случаи, где дополнительная проверка помогла только одному из вариантов. Метки и семейства доступны только оценщику. Для испытания с моделями добавьте `--model`. Чтобы измерить перенос на новые ситуации, храните некоторые семейства в закрытой выборке до финальной оценки.

Опция `--cross-examine` запускает локальный эксперимент со сменой ролей Red и Blue при бюджете одной проверки на сценарий в каждом варианте. [Протокол эксперимента и первый результат](docs/prototype.md#эксперимент-со-сменой-ролей)

## Поиск пробелов в телеметрии

`observe-gaps` находит пары SSH-эпизодов, которые выглядят одинаково по доступным событиям, хотя один эпизод закрыт, а другой требует эскалации. Команда измеряет, какие из дополнительных источников различают эти пары и сколько различий сохранится при потере источника.

```sh
python3 -m arachne observe-gaps arachne/data/trial.jsonl
```

Команда умеет сравнивать новые сигналы и переносить выбранный набор источников на отложенные семейства эпизодов. [Методика, формат данных и результаты](docs/observability.md)

Red и Blue могут независимо предложить, какую улику стоит собирать, затем обменяться предположениями и сформулировать составную проверку. Эксперимент `compare-signals` сравнивает эти предложения с фиксированной проверкой и одиночным агентом после раскрытия подготовленных измерений. [Запуск и первый результат](docs/signal-experiment.md)

## Проверка файлов по индикаторам

```sh
python3 -m arachne scan-files /path/to/test-files --indicators indicators.jsonl
```

Каждая строка списка содержит `sha256` и `label`. Используйте список из доверенного источника. Сканер открывает только обычные файлы, пропускает символические ссылки и специальные файлы, ограничивает объём чтения и сообщает о неполных или недоступных результатах. Код выхода 2 означает найденный индикатор, 1 — ошибку запуска, 0 — отсутствие совпадений в прочитанном объёме. SHA-256 даёт проверку точного совпадения с известным файлом. Для проверки открытия, чтения и совпадения используйте безопасные контрольные файлы. Операции над найденными файлами остаются у оператора.

## Наблюдение за файлами

Создайте исходный снимок на папке с ожидаемым содержимым, затем выполните повторную проверку после изменений:

```sh
python3 -m arachne --db linux.sqlite3 integrity-baseline /path/to/test-files --name 'Тестовая папка'
python3 -m arachne --db linux.sqlite3 integrity-check BASELINE_ID
python3 -m arachne --db linux.sqlite3 integrity-list
```

Вывод первой команды содержит `BASELINE_ID`. Панель показывает последние изменения во вкладке «Целостность файлов». Сохраняются относительный путь, хэши и права доступа до и после изменения. Возврат к исходному состоянию фиксируется отдельным событием. Код выхода `integrity-check`: 0 при полном проходе без новых изменений, 2 при изменениях, 3 при неполном проходе. Неполный проход оставляет последний полный снимок и отмечается в панели. Сканирование периодическое: изменение, случившееся и исчезнувшее между проходами, может остаться незамеченным. Храните рабочую базу за пределами отслеживаемых папок.
